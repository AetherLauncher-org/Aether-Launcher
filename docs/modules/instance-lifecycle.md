# 实例生命周期

实例是「一份可启动的游戏版本 + 它自己的配置与存档」，`aether-storage` 与 `aether-core` 负责它的落盘形态、写入时序和导入语义。这篇讲概念与不变量，不列具体类型和函数名——名字以代码为准。

## 实例目录布局

一个实例就是 `instances/` 下的一个目录，记录文件固定叫 `instance.json`：

```text
instances/
  3f2a9c14-7b60-4e8d-9a11-0c5b2e6f1d37/
    instance.json          实例记录：显示名字、版本指向、启动参数等
    minecraft/             该实例隔离的游戏目录（mods、saves、config 等）
  8b1d0e42-5c3a-4f77-b0e9-2d6a1c8f4b55/
    instance.json
    minecraft/
```

托管实例里的游戏目录名是 `minecraft`，没有前导点（源码常量 `MINECRAFT_DIR`）。导入源里的 `.minecraft/` 是**导入源**自己的目录（见 `crates/aether-storage/src/import/`），导入后它的内容映射到托管实例的 `minecraft/`，两者不是一回事，不要按字面把带点的目录名搬过来。

**游戏就在 `minecraft/` 里运行。** 启动时游戏的工作目录（`--gameDir`）是实例的 `minecraft/`，所以存档、mods、资源包、光影、配置和日志都在那里，`instance.json` 旁边不放游戏文件。早先的版本把实例根目录当作游戏目录，已经启动过的实例会在下一次启动时把 Minecraft 自己的那几项（`saves`、`mods`、`resourcepacks`、`shaderpacks`、`config`、`screenshots`、`schematics`、`logs`、`crash-reports`、`options.txt` 等固定名单）从根目录移进 `minecraft/`：只移普通文件和文件夹、不跟随链接、目标已存在就不动，所以不会覆盖任何东西，重复执行也不会再变。

几条硬规则：

- **目录名就是实例 UUID。** 不是显示名字，不是列表里的序号，也不是版本号和时间的拼接。UUID 在创建时生成，此后不再变化。
- **记录文件名只有 `instance.json` 这一种。** 不存在 `instance.yaml`、`instance.json.bak`、`<uuid>.json` 这类变体；布局里不允许出现可选的第二写法，否则「读哪一份」会变成实现细节。
- **改名不动目录。** 修改实例的显示名字只改记录里的字段，目录名保持原 UUID。这样任何已经保存的路径引用（最近启动列表、快捷方式、外部脚本）不会因为改名失效。记录里只有一份显示名字，就是 `name` 字段本身；改名时改写这一份、`id`、`root`、`version`、`state` 都从磁盘上的记录原样保留。**待实现确认**：前端列表的显示名缓存何时失效（由后端事件推送还是前端重新拉取），取决于最终的 IPC 形态。
- 实例目录本身可以被整体移动，但移动后实例仍以目录名为身份。目录名与记录内 UUID 不一致时以校验为准：两者按 ASCII 大小写不敏感比较，不等则这一项被跳过并报 `id-mismatch`；记录的根路径必须指向它所在的目录，否则报 `root-mismatch`。也就是说「以记录与位置是否自洽为准」，不会挑其中一边硬用。

## 原子写协议

记录文件的写入一律走「临时文件 + rename」，不直接覆盖目标：

1. 在**目标文件所在目录**下创建临时文件，写入完整内容并 flush。
2. 关闭临时文件。
3. 把临时文件 rename 到 `instance.json`。

要点只有两条，但都不能省：

- **临时文件必须与目标同目录。** 放在系统临时目录再 rename 过去，一旦跨卷（系统盘与实例盘不同）就不是原子操作，退化成「复制 + 删除」，崩溃窗口重新出现。
- **rename 之前不碰旧文件。** 不截断、不预先删除、不先写一份空文件。旧文件在被 rename 覆盖前始终是完整的。
- **一次写入只产生一次 rename。** 不要在同一个目标上分多步写（先写元数据、再补字段），那样中途崩溃会得到一个「新旧的混合体」；要改就把整份记录重写一遍。临时文件名固定为 `instance.json.tmp`，与记录同目录，上一次中断留下的同名文件由下一次写入复用。

由此得到的结果是：任何时候断电或进程被杀，磁盘上要么是完整旧记录，要么是完整新记录，不存在「写了一半的 `instance.json`」。读取方因此不需要处理截断的 JSON，只需要把读不出的情况归入 `decode-failed`（见下一节）。

## 列表扫描的容错

列出实例时逐个目录尝试读取记录，**单个坏实例不影响整体列表**：目录不是实例、是链接、记录缺失、记录过大、记录不是普通文件、记录解不开、ID 与目录名不符、根路径不符，都只让这一项被跳过，其余实例照常返回。

跳过项携带一个**稳定的分类字符串**，而不是原始路径，也不是底层错误消息的拼接结果：

| 分类字符串 | 什么情况产生 | 前端应当怎么呈现 |
| --- | --- | --- |
| `not-a-directory` | 该名字存在，但不是目录（是文件，或是拒绝检查的 junction 一类对象） | 说明这里不是实例目录，建议删除后重新创建 |
| `symbolic-link` | 该名字是符号链接，扫描时不会跟随 | 说明实例目录被链接替换过，请改回真实目录 |
| `missing-record` | 目录下没有 `instance.json`，或该名字的元数据读不到 | 记录文件缺失，可能已被手动删除 |
| `record-too-large` | 记录文件超过大小上限（128 KiB） | 记录异常偏大，无法自动读取，请检查或重建 |
| `unsafe-record` | 记录不是普通文件：是目录、是链接，或除「不存在」之外的元数据错误 | 记录文件被替换成别的东西，请检查后重建 |
| `decode-failed` | 文件存在但读不出，或不是能解码成实例记录的 UTF-8 JSON | 记录已损坏，无法读取 |
| `id-mismatch` | 记录里的实例 ID 与目录名不一致（比较时忽略 ASCII 大小写） | 目录被复制或改名过，记录的归属无法确认 |
| `root-mismatch` | 记录的根路径经规范化后不指向它所在的目录 | 记录指向别处的目录，可能由整体搬迁造成 |

这些字符串是 IPC 契约的一部分，必须与 `list.rs` 的 `SkipReason::as_str` 保持一致，改动即为破坏性变更。

另外两条与呈现有关的限制：只有名字形如 UUID（36 字节、`8-4-4-4-12` 布局）的目录失败时才会进入这个清单，其它名字（`versions/`、编辑器备份、临时目录、写到一半留下的 `instance.json.tmp`）一律静默忽略，不会出现在跳过项里；`skipped` 里只有目录名和分类字符串，没有绝对路径。

**面向用户的文案不在后端拼。** 后端只回传分类字符串，中文句子由前端（展示层）按分类映射。这样做有两个具体理由：

- 分类字符串有限、稳定，可以对它写断言；错误消息文本会随底层库版本、系统语言、路径长度变化，无法稳定断言。
- 分类字符串可以整体本地化；如果后端直接返回中文句子，就锁死了界面语言。

## PCL2 / HMCL 导入

导入的核心语义是「**只补缺失文件**」。当前实现停在「检测 + 规划」这一步（`crates/aether-storage/src/import/` 的 `detect`、`plan_candidates` 与 `ImportCandidate`）：它只读目录清单，判定来源启动器，并为识别出的每个版本产出一份计划，把计划里的路径分成「已存在、必须跳过」和「缺失、需要新建」两组。模块本身不复制、不移动任何文件，`mods/`、`saves/`、`config/` 也不会随导入搬运；真正落盘交给消费这份计划的后续步骤。

1. 扫描导入源目录，得到一份相对路径清单（有深度与条目数上限，符号链接跳过）。
2. 判定来源是 PCL2 还是 HMCL；两者标记并存时按 PCL2 处理。
3. 为每个 `versions/<id>/<id>.json` 产出一个导入候选，并按目标侧已有文件把计划拆成「已存在」与「缺失」。
4. 只创建缺失的那部分，已存在的路径一律不动。

为什么必须这样：用户几乎一定已经手动改过东西。jar 可能被换成另一个构建，mods 目录里可能多出几个自己下载的、配置文件可能已经调过内存和窗口。覆盖会直接毁掉这些修改，而且用户通常在被毁掉之后才发现。

注意与上一节 `.minecraft/` 说法的关系：导入源里的版本目录可能位于源的根目录，也可能位于源的 `.minecraft/` 之下，规划结果记录的是这种**相对源**的游戏目录；映射到托管实例时一律落到 `minecraft/`，不带前导点。

对「文件存在但内容不同」的处理：**保留用户文件，不改写**，把该路径归入「已存在」一组，由用户自己决定。**待实现确认**：是否存在单独的冲突清单、以及是否提供「以导入源覆盖」的显式选项；在确认之前，默认行为按「不覆盖」理解。

## 不做什么

- **不复制大文件。** 导入不搬运整份 jar，也不搬运资源包、光影包这类目录。它们要么走下载引擎的链接，要么就地引用，不在导入里做逐字节复制。
- **不执行 installer。** 不运行第三方安装器或 `.exe`、脚本。导入只读取源实例的数据，不执行其中的任何内容，即便源声称需要安装器来完成。
- **不解析完整 INI。** PCL2 的配置只读取判定所需的最小字段（例如版本指向），不做完整 INI 解析，也不写回。配置语法、注释、重复键这些细节不进入导入流程。
- **不迁移用户数据到别处。** 导入不移动、不删除源目录中的任何文件。

## 不变量

以下四条在任何路径上都成立，违反即为缺陷，不是「实现选择」：

- **目标文件只在完整时出现。** 半成品只存在于临时名下，不会落到 `instance.json` 这个最终路径上。任何读方遇到的 `instance.json` 都是完整记录或不存在。
- **跳过项不含绝对路径。** 列表与导入结果只回传分类字符串、实例 UUID 和实例内的相对路径，不回传本机绝对路径——避免通过日志、截图、错误上报泄露用户的目录结构。
- **导入不覆盖已有文件。** 目标路径已存在时，导入只能跳过或记录冲突，不能写入。
- **路径一律经校验。** 从记录、清单、导入源里读到的每个路径都要检查：拒绝包含 `..` 的穿越、拒绝绝对路径、拒绝任何解析后逃出实例目录的结果。校验在拼接之后、打开之前做，对符号链接与 Windows 的盘符前缀同样适用。
