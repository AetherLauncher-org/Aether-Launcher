# 下载引擎

`aether-download` 负责生成下载计划并校验路径；本文讲计划之后的执行部分：发请求、写盘、失败之后怎么办。目标是任何一次中断都不会留下一个「看起来成功」的坏文件。

## 传输 trait 的边界

网络调用只出现在一个传输 trait 后面。它只负责「取一段字节」：给一个地址和可选的字节范围，返回状态码与字节流；`Content-Length` 与 `Content-Range` 被解析成结构化字段，**其它响应头不下传**（这也是 `Retry-After` 接不进来的原因）。

**不包含**：重定向策略、校验、写盘、重试。这些都留在引擎里，因为它们是必须被测试覆盖的策略，而不是传输层的实现细节。

- 测试用内存替身，可精确构造 200、206、404、429、5xx、超时、以及「内容与声明的 SHA-1 不符」。
- 真实 HTTP 实现是独立模块，**不进纯逻辑测试的编译路径**。**待实现确认**：`HttpTransport` 目前只有内存替身，连接池、代理、TLS、重定向策略的真实实现尚未提供。
- CI 既无凭据也不允许访问真实域名；测试里出现真实域名算缺陷，而漏掉一处补丁就算违规。

## `.part` + 原子 rename

对一个目标文件，写盘协议是：

1. 在目标同目录写临时文件 `.part`，边收边写，不先整块读进内存。
2. 边写边算 SHA-1，不落地后再整文件读一遍。
3. 大小与摘要都对得上，才把 `.part` rename 到目标路径。
4. 任何一步失败，删除 `.part`，目标文件保持原状。

三条约束：

- **临时文件必须与目标同目录。** 跨卷 rename 不是原子操作，会退化成复制再删除。
- **校验失败删除 `.part`。** 留着会让人误以为「快下完了」；坏文件一律丢弃，下次从头来。
- **rename 之前不碰目标文件。** 目标文件的旧内容在成功前一直有效，覆盖式写入会让一次失败毁掉可用副本。

## Range 续传语义

续传只看两件事：`.part` 当前多大，服务端实际回了什么。

| 服务端响应 | 语义 | 处理 |
| --- | --- | --- |
| 206 | 只返回请求的区间 | 追加写入 `.part`，写前核对偏移与总大小 |
| 200 | 服务端无视 Range，返回全量 | 必须截断 `.part` 从头重下，否则内容会拼接成长度翻倍 |
| 206，但 `Content-Range` 起点与 `.part` 长度不一致 | 本地前缀与远端对不上 | 删除 `.part` 后失败重来，禁止按错误偏移拼接 |
| 任意，`.part` 不小于总大小 | `.part` 已损坏 | 丢弃重下，不要试图裁剪 |
| 任意，无 `Content-Length` | 总大小未知 | 进度不显示百分比，只显示已下载字节。**待实现确认**：进度事件的总长恒取自计划的期望大小，未知总长的专项处理尚未接入，`total == 0` 时如何呈现仍由调用方决定 |

「全量重来」比「猜着拼接」便宜。不要把服务端给了 200 时的第一个字节误认为是续传的下一块。

## 重试与退避取舍

重试只针对「下次可能就好」的失败：

- **只重试**：超时、连接中断、429、5xx。
- **不重试**：404、403、校验不符。同一结论上重试只是浪费时间。

退避三条：

1. **次数与总时长都有上限。** 到点直接报失败，让用户看见原因，而不是无限转圈。
2. **指数退避带抖动。** 多个文件同时失败时，固定间隔会让它们在同一刻一起重来。**待实现确认**：`RetryPolicy::delay_for_attempt` 目前只算 `base * 2^(n-1)` 并被 `max_delay` 截断，没有随机分量，抖动尚未加入。
3. **测试禁用真实 sleep。** 睡眠走可替换抽象（`DownloadEngine::with_sleeper`），断言「第几次尝试、等了多久」，而不是真的等待。

`Retry-After` 尚未接入：`TransportResponse` 目前只暴露状态码、内容长度、是否支持 Range 与 `Content-Range`，不暴露响应头，所以 429/503 上的 `Retry-After` 读不到、也没有被用作等待时间。接入后需要**封顶**：服务端给一小时就当作本次不可用，不能照着等。

## 多源回退与熔断

一个文件通常有多个来源。**来源只改地址，不改内容身份**：期望的大小与 SHA-1 始终来自官方元数据，换源不换目标。

- 尝试顺序由来源选择器决定：有效权重高的在前，权重相同则连续失败少的在前，再相同保持原始顺序。成功后记住该来源，同批文件优先用它。
- **按来源**记熔断状态：连续失败到阈值（默认 3，可配置，`0` 关闭）就把该来源权重压成 `0` 并在本次会话内不优先使用，而不是每个文件都去撞一次。一个源坏了不影响其它源。**待实现确认**：熔断目前只降权、没有冷却期计时，失败计数随引擎实例走，不落盘。
- **校验不符比超时惩罚更重。** 内容错了比慢更严重，因此计划按更高的权重计入熔断。
- 失败记录五类信息：来源名、目标相对路径、第几次尝试、状态码（来自传输错误）、失败分类。

早期对 BMCLAPI、高校镜像、加载器 maven 和内容平台的调研笔记保存在本地 `docs/excluded/download-sources.md`（该目录已由 `.gitignore` 排除，不随仓库发布），其中的校验契约（provider 只换地址不换身份、失败要记录 provider/artifact/attempt/status/reason、429/5xx/超时有限重试、校验失败丢弃临时文件、缓存状态 `pending | ready | failed | stale`）是对本模块的要求；已实现的是前四条与 `failed` 一种状态，`ready` / `stale` 两种缓存状态的落盘**待实现确认**。

## 进度与取消

- **进度按字节，不按文件数。** 300 MB 的资源包和 4 KB 的元数据文件不该各占一格。
- **取消是协作式的**，不是强杀线程：信号在发起请求前与每次读块前后检查，在下一次检查点生效，不会打断正在进行的阻塞读。
- 取消后**留下 `.part`**，以便下次续传；但校验失败留下的 `.part` 必须删除。
- **取消不弹错误。** 用户按了取消就是取消，不是异常，也不重试、不换源。

## SHA-1 定位

清单里的 SHA-1 **是元数据校验，不是签名**。它只证明「下载到的字节与清单声明一致」，**不证明来源可信、不防篡改**——清单本身也可能被替换。

- 副作用有限但真实：能发现镜像给了旧文件或坏文件、续传拼错、传输被截断。
- 因此 UI 文案**不得暗示「已通过安全校验」「文件安全」**，只可表述为「与清单一致」。
- 传输层可信度（HTTPS、清单来源）是另一层问题，不在本模块解决。
- 校验契约的可选参考：见上文 `docs/excluded/download-sources.md`（不随仓库发布）。清单 URL 的签名规则细节：待实现确认。

## 不变量

1. 目标文件只在完整且校验通过后出现；rename 之前目标不变。
2. 校验失败一定删除 `.part`，且错误类型标明是校验失败而非网络失败。
3. 临时文件与目标同目录，rename 必须原子。
4. 来源只改地址，大小与摘要来自元数据。
5. 重试次数与总时长都有上限，测试不真实等待。
6. 取消与失败是两种状态，不共用同一个错误。

## 不做什么

- 不做签名验证，也不宣称做了安全检查。
- 不实现单文件分片与 P2P。并发度由调用方通过 `concurrency` 参数传入：`download_plan(plan, concurrency, …)` 按 artifact 起 worker（按文件并发，不是单文件分片），默认值与上限**待实现确认**（当前 `concurrency` 被夹到 `1..=artifact 数`，传 `0` 等同 `1`）。
- 不在客户端或 CI 里存放内容平台密钥。
- 不清理下载目录之外的残留文件，也不做磁盘配额管理。
