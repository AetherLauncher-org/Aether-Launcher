# 原生界面

记录从 Tauri + React 外壳改成原生界面的决定、顺序和验收条件。**这份文档与 [ui-shell.md](ui-shell.md) 冲突的地方以这份为准**（ui-shell.md 描述的是现在的 React/Fluent 外壳，原生界面做完、替换掉它之后再删）。

## 决定

2026-10-31，项目负责人决定：**界面改成原生的，不再用 Tauri**。工具包先不定，做一轮对比后再选。

## 为什么

- 三个系统用三个渲染引擎（Windows 的 WebView2、macOS 的 WKWebView、Linux 的 WebKitGTK），行为不一致；WebGL 的 3D 预览在 WebKitGTK 上最不可靠。
- 网页不能控制渲染引擎里自带的界面。例子：抓取鼠标时 WebView2 会弹「按 Esc 显示光标」，网页关不掉。
- 3D 预览要「按显示器刷新率走、在 Minecraft 官方最低配置的机器上也不掉帧（2026-10-31 负责人定：最低硬件要求与 Minecraft 一致，不再是 1 核 1 GB；最低配置上所有功能都要流畅，配置更好的机器可以开更多，例如更大范围的投影原理图预览）」。浏览器里 `requestAnimationFrame` 跟着垂直同步，画不快过显示器，内存基线也高；原生可以直接用 wgpu。
- 体积不是用户在意的事，所以 Tauri 最大的优点用不上。

## 不变的

- **Rust 核心不动**：`aether-*` 各 crate 没有任何 Tauri 代码，原样保留。
- [启动与进程](launch-and-process.md) 里的安全约束一条不放宽：界面只能通过窄的、登记过的操作调用核心；不加「执行任意命令、读写任意路径」的入口；凭据不进日志、序列化和界面；下载只信官方清单；清单、日志、崩溃报告、投影文件都是不可信输入。
- Apache-2.0：选工具包时许可证要兼容（不能把 GPL 链进来）。

## 顺序

1. **把业务逻辑从 `src-tauri` 搬进 `aether-app`**（启动与进程里早就写了这一层）。它不依赖任何界面：需要的外部能力（数据目录、某个实例的游戏是否在运行、之后还有事件推送）由一个 `Host` trait 提供。`src-tauri` 退化成「参数转换 + 调 `aether-app`」。这一步对 Tauri 版和原生版都有用，每搬一块，应用都还能正常运行。
2. **做一轮对比**，在三个候选工具包（iced、egui、Slint）上各做同一个小范围：实例列表、一个有中文输入框的表单、3D 预览。比：中文输入法（IME）、外观、帧时间、内存、编译体积、许可证。结论写回这份文档。
3. **逐页重写**原生界面，页面对页面地对照现在的 React 版。
4. **替换**：功能对齐之后换掉 Tauri 外壳，删除 `src-tauri`、`src/`（React）和这里对 ui-shell.md 的覆盖说明。

第 1 步做完了：实例、管理、投影、微软登录、模组和资源包识别、皮肤、版本目录、原版安装、模组加载器安装、导入、Java、启动都在 `aether-app` 里，`src-tauri` 只剩参数转换和事件转发。界面需要的外部能力（数据目录、游戏是否在运行、登录/安装/导入进度的事件、文件夹和文件选择框、常用文件夹）都在 `Host` 这一个 trait 里。第 2 步做完了（见下面「对比结果」）：三个候选都做了同一个小范围并量过；负责人在真机上试了 iced 和 egui 的中文输入，两个都没问题，Slint 的输入还没试。

## 工具包的验收条件

任何候选都要过这几条，过不了就不选：

- **中文输入法**：能输入、能选词、候选窗口跟着光标、能和快捷键共存。
- **许可证**：与 Apache-2.0 的发行方式兼容。已知 Slint 是 GPL-3.0、免版税协议（要署名）或商业三选一，GPL 不能用，免版税协议要项目负责人确认接受。
- **3D 预览**：能接 wgpu 之类，不被界面框架的重绘节奏拖住；开着一个静止的 3D 画面时 CPU 占用接近 0。
- **可访问性**：键盘能走完所有操作；读屏至少能读出控件名。做不到的要写明。
- **外观**：深浅色主题、可以做出现在 Fluent 那样的层次感（不要求像素级一致）。

## 对比结果（2026-10-31）

代码在 `spikes/native-ui/`，不属于启动器的构建（自己的 workspace，根目录的检查不编译它）。三个候选各做同一件事：用 `aether-app` 列出实例，一个改名表单（输入框里输中文），一个 16×16×16 的方块网格（约 2200 个方块、8 万个顶点，一次实例化绘制，替身 3D 预览），用 wgpu 画。三边共用数据、表单逻辑、方块和量法（`common/`），只有工具包不同。版本：iced 0.14.0（wgpu 27），egui/eframe 0.37.0（wgpu 30），Slint 1.18.1（wgpu 30，femtovg 渲染器）。

Slint 一开始没做，理由是它的许可证要负责人同意才能用。那个理由是错的：对比只在本机跑，不发布任何东西，许可证只决定「能不能选它」，不决定「能不能试它」。负责人指出后补做了。

测试机：GTX 1660 SUPER，1920×1080，显示器 59 Hz，Windows 11。**不是最低配置的机器（Minecraft 官方最低配置的集成显卡），所以下面的帧时间说明不了那一条。** 运行 `spikes/native-ui/bench.ps1` 可以重测，原始输出在 `bench-results.txt`，截图在 `screenshots/`。下表是三个一起跑的那一次（每格两次运行）。**这次跑的时候机器上还有别的活在干（编译、别的程序），所以「最大帧」比之前只跑 iced 和 egui 的那次更吵；那一次 iced 的最大帧约 22 ms、egui 约 50 ms，这次 iced 28–65 ms、egui 68–89 ms。看趋势，不要看单个数。**

| | iced | egui | Slint |
| --- | --- | --- | --- |
| 稳态帧率（转动，10 秒） | 59.8 / 60.0 fps | 59.6 / 60.0 fps | 59.9 / 60.0 fps |
| 帧间隔 p99（含启动） | 19.7 / 24.9 ms | 24.4 / 22.0 ms | 20.0 / 22.3 ms |
| 帧间隔最大值（含启动） | 65 / 28 ms | 68 / 89 ms | 268 / 74 ms |
| 超过中位数 1.5 倍的帧 | 2 / 6 | 8 / 4 | 1 / 2 |
| **稳态 CPU（转动，占一个核）** | 9.1% / 6.4% | 8.3% / 7.5% | **45.0% / 43.7%** |
| 静止时稳态 CPU | 0.3% / 0.3% | 0.0% / 2.5%（第二次被输入事件弄醒过，见下） | 0.0% / 0.6% |
| 静止时 10 秒内重绘的帧数 | 0 / 0 | 0 / 65（同上） | 0 / 0 |
| 内存（工作集，转动 14 秒后） | 约 168 MB | 约 218 MB | 158–196 MB |
| 发布版体积（未 LTO） | 11.7 MB | 14.0 MB | 20.2 MB |
| 发布版编译时间（`-j 2`，冷） | 6 分 40 秒 | 7 分 09 秒 | 11 分 23 秒 |
| 依赖 crate 数 | 484 | 465 | 643 |

怎么读：

- **帧率**三个都咬住了垂直同步（16.67 ms 的间隔），转动时都是 60 fps。抖动上三个没有稳定的差别：这次 iced 和 Slint 的「超过 1.5 倍中位数的帧」比 egui 少，但上一次（机器闲）是 iced 0、egui 4–7，几次放在一起只能说 egui 偏多，不能说 iced 和 Slint 谁更稳。每次只有 600 个稳态帧、两次运行。
- **Slint 的 CPU 是这一轮最大的发现，原因没查清**：转动时占一个核的 44% 左右，是 iced 和 egui 的五到七倍，帧率照样是 60。静止时它不重绘、CPU 接近 0，所以不是空转，是每一帧都花得多。可能是 femtovg 渲染器每帧重画整个界面，也可能是我这个对比里「每帧请求重绘」的写法，没有剖析过，**不能据此说 Slint 一定慢**；要下结论得换 Skia 渲染器再量，并做一次剖析。在最低配置的机器上这个数字会更要紧。
- **静止时**三个都不重绘（Slint 启动时画了 2 帧，iced 1 帧，egui 5–7 帧），CPU 接近 0，满足「静止的 3D 画面 CPU 接近 0」。egui 第二次静止那一轮有 65 个重绘帧和一次 6 秒的停顿：那次测的时候有人在用这台机器，窗口一出现鼠标就在上面，egui 一有输入事件就重绘，这一格不当结论。
- **内存**是进程工作集，里面有 NVIDIA 驱动映射的主机内存，集成显卡上会不一样；iced 比 egui 少约 50 MB，Slint 在两者之间或更高，方向可信，绝对值不能照搬。
- **3D 接入**：iced 的 `shader` 控件把 wgpu 设备和窗口的渲染目标交给自己，自己开渲染通道、自己管深度缓冲，直接画在窗口里。egui 的渲染通道没有深度缓冲给我们用，所以先画到自己的纹理，再让 egui 当图片贴出来。Slint 同样是画到自己的纹理，再用 `slint::Image::try_from(wgpu::Texture)` 导入，设备和队列从 `set_rendering_notifier` 里拿；Slint 要开 `unstable-wgpu-30` 特性，文档写明这个接口「可能在小版本里改动或删除」。
- **中日文显示**：iced 和 Slint 用系统字体，不用做任何事，中文、日文（サバイバル）都对。egui 不看系统字体，要自己找一个 CJK 字体文件读进来（`msyh.ttc` 等），找不到就显示成方框；Windows、macOS、Linux 要分别写路径，这是要长期维护的东西。
- **输入法**：负责人在真机上用过 iced 和 egui 的输入框，**两个都没有问题**。Slint 的 `LineEdit` 也有输入法支持，但没有人在真机上试过，所以 Slint 这一条是空的。
- **许可证**：iced 和 egui 的依赖树都没有只能按 GPL 用的东西，标出来的三个（`r-efi`、`self_cell`）都是双许可、有宽松选项。iced 是 MIT，egui 是 MIT 或 Apache-2.0。**Slint 的每个 crate 都是 `GPL-3.0-only OR Slint Royalty-free 2.0 OR Slint Software 3.0`**：GPL 不能用（项目是 Apache-2.0）；免版税协议要求署名，并有它自己的条件，用它要负责人读完条款后同意；第三种是付费商业许可。这是 Slint 能不能选的前提，不是性能问题。
- **可访问性**：egui 带 AccessKit（开了 `accesskit` 特性，没有用读屏软件测过）。Slint 也带 AccessKit（`accessibility` 特性，同样没有测过）。**iced 0.14 没有可访问性支持**，它的依赖里没有 AccessKit。验收条件写了「做不到的要写明」：选 iced，读屏读不出控件名，键盘能不能走完所有操作要另外验证。
- **外观**：见 `screenshots/`。iced 默认的深色主题比 egui 的默认外观精致，圆角、留白和层次都更接近现在的 Fluent；egui 默认偏工具软件，要做出同样的层次要自己调很多；Slint 默认的深色控件介于两者之间，用的是自己的 `.slint` 描述语言写界面，要多学一门东西。三者都没有做 Fluent 的令牌映射。
- **iced 能不能做成 Fluent 的样子**（负责人问过）：能。`spikes/native-ui/iced/src/fluent.rs`（约 230 行）把 `brand.ts` 的品牌色阶、Fluent 的中性色和 4 / 8 px 圆角做成了一个 iced 主题加几个样式函数（卡片、页面层、主要 / 次要按钮、导航项、输入框），`screenshots/spike-iced.png` 是结果。没有 CSS、没有现成的 Fluent 令牌集、没有悬停过渡动画（要自己按时间插值），这一层要自己维护；Mica 之类的窗口材质要在窗口层另外接 winit 和 Windows API，这次没做。
- **API 的稳定性**：iced 0.14、egui 0.37 和 Slint 1.18 的 API 都与我记忆里的版本不同（iced 的复选框、egui 的 `show_inside` 改名、wgpu 27 与 30 的结构差异、Slint 的 `ColorScheme` 是内建枚举不用导入），都是按源码改过来的。三者的 wgpu 接口都是会变的，升级要预留时间。

倾向：**仍然是 iced，但现在它和 egui 之间的真正分歧是可访问性**。iced 内存少、系统字体不用管、3D 直接画进窗口、默认外观更接近要的层次，输入法验过了；代价是没有可访问性。egui 有可访问性、输入法也验过了，代价是字体要自己找、内存多 50 MB、外观要自己调。**Slint 暂时不选**：转动时的 CPU 高得多且没查清，许可证要负责人同意，体积和编译时间最大；它的优点是有 AccessKit 和声明式的界面描述。如果要认真考虑 Slint，先换 Skia 渲染器重量，并由负责人读完免版税协议。

## 待定

- 工具包：iced、egui 还是 Slint（见上）。输入法两个已经验过，剩下的是负责人的取舍：**iced 没有读屏支持能不能接受**（不能的话是 egui 或 Slint），以及是否值得为 Slint 去读免版税协议。
- 如果要考虑 Slint：用 Skia 渲染器重量转动时的 CPU，并剖析那 44% 花在哪。
- 在 Minecraft 官方最低配置的集成显卡（或最接近的机器）上再量一次帧时间，否则「最低配置不掉帧」没有验证。`bench.ps1` 可以直接用。
- 在刷新率更高的显示器上量一次（本机 59 Hz），确认帧预算跟着刷新率走。
- Fluent 设计令牌（`ui-shell.md` 里的颜色、圆角、动效）怎么映射到原生：直接移植数值，还是重新设计。
- Mica 材质：原生窗口可以直接请求，细节看工具包。
- 网站（`site/`）和它的设计规范不受影响，继续用 React。
- 设置、账户等现在存在 `localStorage` 里的东西，原生版要放到应用数据目录里的文件，需要一个迁移。
