# 界面外壳与安装流程

这份文档记录 2026-10 那次界面重做的决定：窗口怎么画、导航怎么收、动效从哪来、安装为什么只有一个按钮，以及还没定的事。

## 为什么重做

第一版界面只是把 Fluent 组件摆进了一个带侧边栏的窗口，用起来有这些问题：

- 没有动画；侧边栏不能收起；窗口带着系统标题栏。
- 品牌是绿色方块里放一个字母「A」，应用图标还是 Tauri 默认的 logo。
- 创建实例的对话框里挤着「缓存 JSON」「下载」「创建」三个按钮和一个内存输入框。
- 没有版本总览：用户得先凭空填一个版本号。
- 添加离线账户是一个直接输入框，没有 UUID 的选择；账户重启后丢失。

## 窗口

- 无边框：`decorations: false`，标题栏由前端自绘（`src/shell/TitleBar.tsx`）。拖动用 `data-tauri-drag-region`，最小化、最大化、关闭三个按钮调用 `src/ipc/window.ts`。
- 窗口权限只开了这几项：`allow-minimize`、`allow-toggle-maximize`、`allow-close`、`allow-start-dragging`、`allow-set-theme`（`capabilities/default.json`）。不提供任意窗口操作的入口。
- Mica：窗口以 `transparent: true` 加 `windowEffects: mica` 创建。Mica 只在 Windows 11 上生效，所以前端用 `navigator.userAgentData` 判断系统版本（`src/lib/platform.ts`），不是 Windows 11 时在 `<html>` 上标 `data-material="solid"`，由 CSS 铺实色背景，避免透出桌面。
- 界面的明暗通过 `setWindowTheme` 同步给窗口，Mica 才会跟着界面变，而不是跟着系统。

## 设计语言

- 颜色、圆角、间距、字号、阴影、动效时长全部取自 Fluent 的设计令牌（`var(--colorNeutralBackground1)` 之类），样式里不写死色值。例外：实色回退时的窗口底色，以及关闭按钮悬停的红色（Windows 标准）。
- 品牌色阶由固定色相、均匀亮度生成 16 级（`src/lib/brand.ts`），再交给 `createLightTheme` / `createDarkTheme`。想换主色只改色相。字体优先 Segoe UI Variable。
- 布局参照 WinUI 的 NavigationView：左侧导航透出 Mica，右侧是一块带描边、左上圆角的内容层；卡片用前景色的 4% 叠加做底，而不是固定灰色，这样深浅两套主题都有层次。
- 选中的导航项用实心图标，左侧有一条 3px 的指示条。

## 导航

- 顶部的汉堡按钮收起／展开，宽度 240 ↔ 52，图标位置不动；收起时悬停显示名称。状态存在 `localStorage`（`aether.navCollapsed`）。
- 底部是当前账户和设置。没有账户时那里引导去添加。

## 动效

- 时长和曲线用 Fluent 的动效令牌（`--durationSlow`、`--curveDecelerateMid` 等），和组件库自带的过渡一个节奏。
- 页面切换淡入并上移；卡片按序号依次浮现；详情页从右侧滑入；导航栏宽度、选中指示条、卡片悬停都有过渡。版本列表有几百行，只整体淡入，不逐行错开。
- 两种关闭方式：设置里的「界面动画」开关（`data-motion="reduced"`）和系统的「减少动态效果」。都把动画压到近乎瞬间，保留最终状态。

## 页面与流程

- **下载**（对应 PCL 的做法）：先是版本总览——顶部是最新正式版和最新快照，下面按正式版、快照版、远古版分组，可以搜索；点进某个版本才是详情和安装。详情里右侧是元数据（类型、发布时间、清单来源、清单 SHA-1、是否支持）。
- **安装只有一个按钮**。用户取一个实例名，点「安装」，后端按顺序完成：获取并校验版本清单 → 下载客户端、依赖库、本地库 → 下载资源索引和全部资源对象 → 创建实例并标记可启动。进度通过 `install://progress` 事件推送，界面显示四步、字节数、文件数、速度和剩余时间，可以取消；取消后已下载的文件保留，再装时已通过校验的文件会被跳过。
- 安装任务放在应用层：切到别的页面再回来，进度还在；标题栏右侧也有一个进度条，点击回到下载页。
- **实例**：卡片网格，每张有封面、名称、版本和启动／停止按钮。实例只能由安装流程创建，没有「创建空实例」。
- **账户**：「添加离线账户」是对话框，填用户名并选 UUID 格式——标准（由用户名生成，与官方离线一致）、随机（创建时生成并保存）、自定义。账户存在 `localStorage`，重启后保留；离线账户没有任何秘密。启动时用当前账户。
- **设置**：外观、内存、Java、下载来源、关于。内存上限只在这里调，创建、安装和启动都不再询问。
  - 内存是「自动」或「自定义」两种。滑块是**一体化**的：整条轨道就是这台电脑安装的物理内存（范围取自 `system_memory`，不是固定数字）。左边红色是系统已经用掉的，不能拖；分界线右边是可用内存，蓝色手柄在里面滑动，蓝色从分界线铺到手柄，就是分配给游戏的量；**橙色手柄一直在分界线上**。两个手柄是同一种**相对**的控制，手柄不会在按下时跳到指针下面，而是跟着指针移动的距离走：蓝色往右、橙色往左都是「多分配」，反之是「少分配」。蓝色没到底时多出来的部分让蓝色往右增加；蓝色到底（「满」，即把可用内存全部分配）之后继续多分配（往右推蓝色，或往左拖橙色），橙色才真的往左走进红区；往少了拖则是橙色先退回分界线，再往下蓝色就直接减少。进了红区的那一段是橙色，界面直接写明「不推荐」（图例、轨道下方、警告各一处）：分配得比可用内存还多，会挤爆内存。为了跟手，手柄位置不加过渡动画，指针拖动按 32 MiB 取整（约 1–2 个像素），键盘方向键仍是 256 MiB 一格。两个手柄控制同一个值；屏幕外还有一个真正的 `<input type="range">`，键盘和读屏用它。下面写着「系统已用 / 总内存」和「游戏分配（可用 …）」，并有图例。读不到已用内存时没有红区和橙色手柄，退化成普通滑块。
  - 自动模式每次**启动**时重新读取可用内存再算：可用内存的 65%，不超过 8 GiB，不超过总内存的 75%，不低于 2 GiB（总内存很小时让位于 75%）。读不到本机内存时用 4 GiB。
  - 只有最大堆（-Xmx）。初始堆（-Xms）要先让 `aether-launch` 的启动请求支持它，暂时没做。
- 内存、账户、实例的启动都不需要用户再确认一次文件校验：启动协调器会在每次启动前重新校验客户端、库和资源。

## IPC 变更

新增：

| 命令 | 作用 |
| --- | --- |
| `install_vanilla_version(version, name)` | 安装一个官方版本并创建实例，返回实例摘要 |
| `cancel_vanilla_install()` | 取消正在进行的安装 |
| `game_status(id)` | 本次会话里该实例的运行状态，让界面发现游戏已退出 |

`start_installed_instance` 新增可选参数 `account_uuid`；不传时由后端按玩家名生成标准离线 UUID，传入的 UUID 在后端再校验一次。

移除：`cache_vanilla_version_manifest`、`install_vanilla_client_libraries`、`create_instance`、`activate_installed_instance`。它们的逻辑合并进了安装流程，前端不再能单独触发「只缓存」或「只创建空实例」。

事件：`install://progress`，载荷是当前阶段的 `{ version, stage, filesDone, filesTotal, bytesDone, bytesTotal }`。

## 待定

- Windows 10 和 Linux 没有 Mica，目前回落到实色背景，细节没有在这两个系统上看过。
- 1.13 之前的版本（`minecraftArguments` 格式）和远古版暂不支持：启动计划只认结构化的 `arguments`。界面按发布日期（2017-10-25，17w43a）禁用它们并说明原因。要支持得先扩展 `aether-launch`。
- 设置里的「默认 Java」只是记录选择，启动时仍由启动器按版本要求自动挑选。要让它生效，需要决定怎么把「选哪个 Java」安全地传给后端（不能直接传路径）。
- 已有但文件不完整的实例（例如安装中途被杀掉的旧记录）目前只能提示「重新安装这个版本」，没有就地修复。
- 只允许一个安装同时进行；多版本排队还没做。
- 微软账户登录还没接通，界面如实显示状态。
- Windows 11 的最大化按钮悬停布局（Snap Layouts）自绘标题栏拿不到，需要的话得再接系统消息。
